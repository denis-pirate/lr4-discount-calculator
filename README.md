# Калькулятор скидок

Лабораторная работа 4 по дисциплине «Разработка web-приложений» (ОмГТУ, группа ИСТ-251).

Калькулятор цены со скидкой и НДС на React. Цель работы: научиться управлять состоянием формы с несколькими взаимосвязанными полями через `useState`, обрабатывать события `onChange` и `onClick`, реализовать расчёт цены со скидкой и НДС.

## Возможности

- Заказ из нескольких товаров (до 10): у каждого своя цена и категория.
- Скидка по категории: Электроника 5%, Одежда 15%, Продукты 10%, Книги 20%, Другое 0%.
- Промокод `WELCOME10`: +10% к скидке каждой позиции (проценты складываются).
- Ручная скидка ползунком 0–50% на весь заказ, заменяет скидку категории.
- Переключатель «С НДС / Без НДС» (ставка 22%, начисляется на цену после скидки).
- Валидация цены по каждой позиции, результат показывается только после нажатия «Рассчитать».
- Промежуточные вычисления: таблица по позициям (цена, скидка, цена со скидкой) и итоги заказа.

Задание 5 из методички (история расчётов) **не выполнено**, см. «Примечания».

## Запуск

Нужен Node.js 20.19+, 22.13+ или 24+ (требование Vite 8 и ESLint 10); проверено на Node 24.

```bash
git clone https://github.com/denis-pirate/lr4-discount-calculator.git
cd lr4-discount-calculator
npm install
npm run dev        # режим разработки, http://localhost:5173
```

Другие команды:

```bash
npm run build      # production-сборка в dist/
npm run preview    # просмотр собранной версии
npm run lint       # проверка ESLint
```

Стек: React 19, Vite 8, ESLint 10, обычный CSS.

## Решения по заданиям

### Базовая версия

Реализована по методичке: четыре состояния `price` (строка), `category`, `calculated`, `error`; обработчики `handlePriceChange`, `handleCategoryChange`, `handleCalculate`, `handleReset`. Формулы:

```
discountAmount     = price × (discountPercent / 100)
priceAfterDiscount = price − discountAmount
vatAmount          = priceAfterDiscount × 0.22
total              = priceAfterDiscount + vatAmount
```

НДС начисляется после скидки, на сумму, которую покупатель реально платит за товар.

### Задание 1. Несколько товаров

- Состояние `items` — массив `{ id, price, category }`; ошибки `errors` — объект по `id` позиции (вместо одной строки `error`).
- `id` нужен как стабильный `key`: при ключе-индексе и удалении из середины React переиспользовал бы не те поля. Счётчик `id` хранится в `useRef`: он меняется только в обработчиках и не вызывает перерисовку.
- Все изменения состояния иммутабельные (`map`, `filter`, spread) и через функциональную форму `setItems(prev => ...)`.
- «Рассчитать» проверяет все позиции сразу; результат показывается, только если ошибок нет нигде.
- НДС и итог считаются от суммы позиций. Максимум 10 позиций, последнюю позицию удалить нельзя.

### Задание 2. Промокод

- Справочник `PROMO_CODES` (массив `{ code, discount }`), как `CATEGORIES`; сейчас один код `WELCOME10`.
- Проценты **складываются**: Книги 20% + 10% = 30%. Верхняя граница `MAX_DISCOUNT_PERCENT = 100` — защита на случай новых промокодов (при текущих данных недостижима).
- Код сравнивается без учёта регистра и пробелов по краям. Неизвестный непустой промокод — ошибка валидации, расчёт блокируется (иначе пользователь решил бы, что скидка применилась). Пустое поле допустимо.

### Задание 3. Ручная скидка

- Один общий ползунок на весь заказ, включается галочкой «Задать скидку вручную». Диапазон 0–50, шаг 1, значение по умолчанию 10.
- Ручная скидка **заменяет** скидку категории у всех позиций; промокод прибавляется сверху (максимум 50% + 10% = 60%). Пока она включена, селекты категорий заблокированы, но выбор в них сохраняется.
- Значение ползунка хранится числом (в отличие от цены): у `range`-input нет промежуточных некорректных состояний, браузер сам держит значение в диапазоне.

### Задание 4. Переключатель НДС

- Состояние `withVat` (булево, по умолчанию `true`), радио-кнопки «С НДС / Без НДС».
- При «Без НДС» НДС не начисляется, итог равен цене после скидки; строка НДС показывает «не начисляется».
- Подписи «22%» берутся из константы `VAT_RATE` (через `VAT_PERCENT`), а не дублируются в разметке.

### Задание 5. История расчётов

Не выполнено.

## Примечания

### Ошибки и неточности в методичке

Разбор сделан по `.pptx`, проверен сборкой кода и прогоном в браузере.

1. **Неразрывные пробелы (`U+00A0`) в коде слайдов.** 11 из 26 CSS-правил (`.calculator-wrapper`, `.field`, `.actions`, `.btn--*`, `.results` и др.) начинаются с `\xa0`. В CSS это не пробел, а часть селектора, поэтому при копировании со слайдов правила не срабатывают. ESLint на скопированном коде даёт 10 ошибок `no-irregular-whitespace`. В проекте код очищен от `\xa0`.
2. **Склеенные закрывающие скобки и потерянные отступы** (`color: #ef4444;}`, `</div>  );}`, комментарии на нулевом отступе на стыках слайдов). Код валиден; отформатирован без изменения содержимого (проверено сравнением с оригиналом с точностью до пробельных символов).
3. **Цель работы противоречит реализации.** В цели заявлен «динамический расчёт», но по методичке расчёт идёт по кнопке «Рассчитать», а любое изменение полей скрывает результат.
4. **Слайд «Обсуждение».** «Результаты пересчитываются при смене категории» — на деле они не пересчитываются, а скрываются. Объяснение, почему цена хранится строкой, неточно: `Number("")` даёт 0, а не `NaN`; настоящая причина в том, что промежуточные значения вроде `"10."` числом не выразить.
5. **Не описаны шаги с файлами шаблона.** Методичка не говорит, что делать с `index.css`, `App.css`, `assets` и `public/icons.svg`. Скриншоты в методичке сделаны с глобальными стилями шаблона Vite (`#root { text-align: center; ... }`): центрованные подписи, боковые линии, сжатая карточка. В чистом проекте вид другой. При тёмной теме ОС и стилях шаблона текст в полях ввода становится белым на белом.
6. **Мелкие несоответствия в коде:** «22%» и `0.22` продублированы в разметке при наличии `VAT_RATE`; `selectedCategory.label` без защиты, хотя выше есть проверка `selectedCategory ?`; условие `!error` в `calculated && !error` избыточно; переменная `numPrice` объявлена и в обработчике, и в теле компонента; `.field__input--error` проигрывает `:focus` по специфичности; `max-width: 480px` без `box-sizing` даёт реальную ширину 544px; комментарий называет `CATEGORIES` словарём, хотя это массив.
7. **Задания для самостоятельной работы** не говорят, сколько из них обязательны, и не определяют взаимодействие между ними (например, как промокод сочетается с ручной скидкой). Решения приняты в разделе «Решения по заданиям».

- **Файлы шаблона Vite.** `src/App.css`, `src/assets/` и `public/icons.svg` удалены (используются только демо-страницей); `src/index.css` заменён на `body { margin: 0; }`; `public/favicon.svg` оставлен. В `index.html` установлены `lang="ru"` и заголовок «Калькулятор скидок».
- **Задание 1:** состояние `price`, `category`, `error` заменено на `items` и `errors`; нулевая скидка выводится как `0,00 ₽` вместо `−0,00 ₽`.

## Известные ограничения

- **Запятая в цене не принимается.** Регулярное выражение `/^\d*\.?\d*$/` допускает только точку; ввод `10,5` молча отбрасывается, что неудобно на русских клавиатурах.
- **Округление только при выводе.** Каждая строка округляется отдельно до копеек, поэтому видимая сумма строк может отличаться от итога на 0,01 ₽. Пример: цена 349,90 ₽, категория «Одежда»: после скидки 297,41, НДС 65,43, итого показано 362,85, хотя 297,41 + 65,43 = 362,84.
- Ввод цены не ограничен сверху.
- Промокод проверяется на клиенте и виден в исходном коде; нет срока действия и одноразовости.
- Ручная скидка и переключатель НДС общие на весь заказ; ставка НДС одна (22%), льготных нет.
- Расчёты нигде не сохраняются: при перезагрузке страницы форма сбрасывается.
- Автотестов нет. Проверялось вручную в десктопном Chromium; на мобильных устройствах не проверялось. Тёмная тема не предусмотрена.

## Ответы на контрольные вопросы

**1. Почему цена хранится в состоянии как строка, а не как число?**
Значение controlled input в React — строка. Во время набора поле проходит через состояния, которые числом не выразить без потерь: пустая строка, `"10."`, `"."`. Если привести `"10."` к числу, получится `10`, точка исчезнет, и ввести `10.5` будет невозможно. Для пустого поля `parseFloat("")` даёт `NaN`, а `value={NaN}` приводит к предупреждению React. Поэтому хранится ровно то, что ввёл пользователь, а в число значение переводится один раз, в момент расчёта (`parseFloat`), после валидации.

**2. Зачем нужен флаг `calculated` и что изменится, если его убрать?**
`calculated` означает «результат актуален и показывать его можно». Он разделяет ввод и расчёт: результаты появляются только после нажатия «Рассчитать» и только при корректных данных. Без флага пришлось бы либо показывать результат всегда (на старте это нули и пустая таблица, а для невалидного ввода — бессмысленные числа), либо перейти на полностью динамический расчёт на каждый символ, и тогда кнопка «Рассчитать» стала бы лишней.

**3. Почему при каждом `onChange` сбрасывается `calculated` в `false`?**
Результат относится к тем данным, которые были на момент расчёта. После изменения цены или категории он устарел, и показывать старые числа рядом с новым вводом значило бы вводить пользователя в заблуждение. Сброс гарантирует, что на экране либо результат, соответствующий текущему вводу, либо ничего. Цена такого решения — после каждой правки нужно нажимать «Рассчитать» заново.

**4. Как работает регулярное выражение `/^\d*\.?\d*$/` в `handlePriceChange`?**
`^` и `$` — начало и конец строки, поэтому проверяется вся строка целиком. `\d*` — ноль или больше цифр, `\.?` — необязательная одна точка, затем снова `\d*`. Подходят `""`, `"12"`, `"12."`, `".5"`, `"12.5"`, `"."`; не подходят `"1.2.3"`, `"1,5"`, `"abc"`, `"-5"`, `"1e3"`. Если значение не подходит, `setPrice` не вызывается, и controlled input остаётся с прежним значением: недопустимый символ просто не появляется. Строка `"."` регулярное выражение пропускает, но при нажатии «Рассчитать» она отсекается валидацией (`parseFloat(".")` даёт `NaN`).

**5. В чём разница между `onClick` и `onChange` для кнопки и поля ввода соответственно?**
`onClick` срабатывает на клик по элементу, то есть на действие пользователя; у кнопки нет «значения», которое могло бы измениться, поэтому для неё нужен именно клик. `onChange` в React срабатывает при каждом изменении значения поля (на каждый введённый или удалённый символ, в отличие от нативного события `change`, которое срабатывает при потере фокуса); текущее значение читается из `e.target.value`. Для поля ввода «клик» ничего не говорит о введённых данных, поэтому здесь нужен `onChange`. По тому же принципу в проекте `onChange` используется у `select`, ползунка, галочки и радио-кнопок.
